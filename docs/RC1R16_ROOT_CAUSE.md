# Guided persistence root-cause report — RC1R16

A precise Core failure was reproduced with the exact official RC1R14 Arabic and English M1 ZIPs, a fresh test class/session and clean browser storage. A normal online acknowledge succeeded. Replacing the actual PUT response with HTTP500 text/html reproduced “Saved on this device. Reconnect to continue.” while navigator.onLine was true. This proves a Core classification defect; the owner's original network trace was not supplied, so its exact upstream response is not asserted.

Affected path: guided.js evidence change -> bindPersonalPractice -> saveGuided -> sendGuidedChange in student.js -> fetch PUT /api/student/runtime/:class -> response.json(). The old adapter parsed JSON before checking response.ok. An HTML500 response threw SyntaxError without status. saveGuided's catch(!error.status) then created a pending outbox row and replaced the server failure with the offline message. The server had not confirmed or committed that intended change. Any preexisting pending row caused later online saves to receive the same reconnect message without sending, making the first defect sticky. The replay worker also treated no-status runtime errors,401 and5xx as pending instead of distinct errors.

Repair: isolated typed transport preserves status before parsing, verifies positive server acknowledgement and mutation identity, and classifies parsing/runtime faults separately. The outbox is durable before first send; confirmed writes are removed, rejected writes retain an actionable category, retries share stable mutation IDs, and immediate save/replay are serialized. Additive transactional receipts make progress and response retries idempotent, including lost replies after commit. Answer revisions prevent stale-tab overwrite. Navigation stays blocked until confirmation; confirmed replay updates a focused renderer rather than leaving its local pending flag stuck. The UI refresh is outside the persistence confirmation boundary.

Regression evidence: unit HTTP/non-JSON500/422/401/403/404/409 and invalid2xx/runtime/network/timeout cases; API all eight evidence/twelve interactions, duplicate/lost/stale mutations, receipts after66 later saves, own-class/path authorization and database integrity; real-browser exact M1 AR/EN eight routes with refresh after answers/evidence, all-mode technical offline/reconnect and actionable online failures. The final release matrix and full source/exact-extraction receipts are authoritative; intermediate runs are not release certification.

Database/API changes: workspace migration0008 adds guided_mutation_receipts; no core/course schema change or reset. Guided writes with client_write_id receive mutation_id,code=CONFIRMED,revision. Embedded responses always require expected_revision and increment the same runtime revision. Outdated Guided tabs/queued answers without revisions require review/reload. Ordinary canonical activity APIs are unchanged. Development diagnostic events omit tokens/private answers and exception bodies.

Additional multi-tab repair: the former unsent-chain rebase matched account/class/path/step/revision but not the originating document. Two independently offline tabs could therefore be treated as one chain. New rows carry a document origin; only that origin's unsent changes can follow its confirmed revision. Explicit two-tab offline replay now confirms the first document and retains the stale second document as a conflict, preserving both the newer server value and local intended edit for review. This is distinct from the proven non-JSON500 false-offline root cause.
