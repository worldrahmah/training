# RC1R13 upgrade and data protection

Back up the existing installation, stop its registered instance, verify the new application ZIP SHA-256 and replace application files while retaining all configured data/storage/backups/exports and local configuration. Use the existing Windows launcher or npm start with Node 22.5+ (engineering checks use 24.19.0). Never enable TRAINING_ENGINE_TEST_ACCOUNTS on owner data.

Core schema remains 3.2; course schemas 1.0/1.1/2.0 remain supported. Journaled workspace migration one-workspace-0005 advances the additive workspace schema from 4 to 5. It adds trash_records and lookup indexes only. The existing upgrade protection creates and verifies a pre-upgrade SQLite/storage backup before pending workspace migration; migration checksums, transactions and populated-history checks are retained. No reset, account replacement, destructive upgrade conversion or published-version rewrite occurs.

Previous Archive records remain Archive because old delete and intentional archive actions were indistinguishable. Move to Trash is available there. New Delete always goes to Trash. Restore retains the original completed/scheduled/archive state and saved responses. Courses in Trash cannot be used for new classes or editing. Existing deliveries of a trashed parent course retain their immutable course version; a course cannot be permanently purged while any class references it.

Permanent deletion is a separate administrator action from Trash. It requires the exact name and explicitly removes a class's responses, progress, submissions, certificates and related records. It keeps an audit entry, removes private dependent report snapshots and unlinks owned stored files; an explicit cleanup-pending outcome is shown if local file removal fails. It never runs automatically or through bulk archive. Permanent deletion cannot be restored from Trash; use the owner's deliberate backup recovery process if required.

Rollback application bytes with a verified previous package and preserve newly collected data. The additive table/indexes can remain during application rollback; do not rewrite schema journals or restore an older database over new learning records as a routine downgrade. Older versions do not implement Trash semantics, so use the pre-upgrade backup only as a deliberate full recovery and avoid operating old and new versions concurrently. Keep the prior sealed package and verified pre-upgrade backup.
